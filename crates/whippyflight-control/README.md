# whippyflight-control

A gain-scheduled LQR attitude-rate controller for quadrotors. `no_std`, no allocation, no globals: it takes sensor data in and returns motor duties, and a firmware adapter does the rest.

Gains are solved offline over a grid of motor speeds and loaded from a `.wfg` blob, generated by the [whippyflight](https://github.com/Oblarg/whippyflight) Python tools from a plant fit.

## Usage

```rust
use whippyflight_control::controller::ControllerState;
use whippyflight_control::gains::{load_gains, GainStorage};
use whippyflight_control::setpoint::SetpointEstimator;
use whippyflight_control::types::*;

// At boot: the blob must stay in static, 4-byte-aligned memory while loaded.
let mut gains = GainStorage::new();
assert_eq!(load_gains(BLOB, &mut gains), GainLoadResult::Ok);
// Then check gains.layout against the firmware's mixer.
let mut setpoint = SetpointEstimator::new();
setpoint.configure_for(&gains);
let mut controller = ControllerState::new();

// Per RX packet:
setpoint.packet(stick_rates, packet_time, rx_period);

// Per loop:
let (rate_rps, target) = setpoint.tick(now, gains.header.dt);
let out = controller.update_with_target(&sensors, &SetpointData { rate_rps, throttle }, target, &gains);
// out.motor_duty: [f32; 4], by the firmware's motor index.
```

## Conventions

Rates and motor speeds in rot/s, voltages in V, specific force in m/s². Output is duty: applied voltage over `SensorData::battery_voltage`. Axes are FRD (x forward, y right, z down), ordered `[roll, pitch, yaw]`. Motors are by the firmware's own index; the blob's layout block records each one's position and spin, and the adapter must check it against its mixer. Only quad X is supported. See `types` and `gains` for details.

## Features

- `std`: host builds (`Debug` impls, `gains::static_blob`, `gains::spec::BlobSpec` for writing blobs).
- `airframe-drag`: compensate rotor-drag torque on tall frames from the accelerometer, when the blob has a drag model.
